## 2025-05-18 - Batching Firestore Queries with Caching
**Learning:** In the Python backend, N+1 Firestore queries in loops (like in `build_syllabus_context`) severely impact performance. However, replacing them with a thread-safe LRU cache and batched `in` queries (chunked to 30) introduces edge cases: you MUST explicitly cache empty strings for successful 'not found' queries to avoid repeated DB hits for missing data, and you MUST re-raise database exceptions instead of swallowing them to prevent cache poisoning. Also, because batch fetching changes result ordering, you must iterate over the original requested ID list to construct the final output. Finally, `time.monotonic()` is preferred over `time.time()` for cache TTL logic to avoid system clock adjustments.
**Action:** When fixing N+1 queries using caches and batching, always ensure missing keys are actively cached as empty/None, exceptions are re-raised rather than swallowed, ordering is deterministically reconstructed, and thread locks do not wrap network I/O.
